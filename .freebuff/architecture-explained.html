2. Folder structure

Each folder answers one question. When you add a feature, you add one file to each folder — you rarely touch files from other features.

├── .env                  # secrets (git-ignored). Copy from .env.example
├── docs/                 # beginner docs: ARCHITECTURE.md, AUTH.md
└── app/
    ├── app.py             # the app: startup hook + list of routers

3. The four layers (and the one rule)

Arrows point down only. A model never imports a router; a service never knows HTTP exists. That rule is what keeps code testable and swappable.

Notice

Schemas run first. Garbage JSON never reaches your logic — Pydantic rejects it with 422.

Notice

Deps run before route bodies. No token? Your endpoint code never even executes.

Notice

Services are plain functions. You can test verify_password() without a server or a browser.

4. A request's life, step by step

Pick an endpoint and follow one request from the wire to the database and back. These are the exact routes that exist today — including the bill photo.

  1. routers/auth.py

    FastAPI matches POST /auth/register and hands the JSON body over.

  2. schemas/auth.py

    Pydantic checks UserCreate: email present, password 6–72 chars. Wrong? → 422, stop here.

  3. services/db.py

    A fresh database session opens; query: SELECT * FROM users WHERE email = ?.

  4. branch

    Email already exists → 409 Conflict. (Never reveal whether a password was right — same idea later on login.)

  5. services/auth.py

    hash_password() runs bcrypt with a random salt → a hash string. The plain password is discarded.

  6. models/user.py

    New users row is inserted and committed.

  7. response

    201 {"id": 1, "email": "ana@example.com"} — shaped by UserOut, so the hash can't leak.

  1. routers/auth.py

    FastAPI matches POST /auth/login.

  2. schemas/auth.py

    Pydantic validates UserLogin → bad shape is 422.

  3. services/db.py

    Look up the user by email (lower-cased, so Ana@ = ana@).

  4. services/auth.py

    verify_password() → wrong password or unknown email → same 401 message. Attackers can't probe which emails exist.

  5. services/auth.py

    create_access_token(user_id) signs a JWT: {"sub": "1", "exp": …} + SECRET_KEY.

  6. response

    200 {"access_token": "eyJ…", "token_type": "bearer"}. The server stores nothing — the token is the session.

  1. header

    Client sends Authorization: Bearer eyJ….

  2. deps.py

    get_current_user runs before the route body. No header → 401, full stop.

  3. services/auth.py

    decode_access_token() verifies the signature and expiry. Forged or expired → 401.

  4. models/user.py

    Token says sub=1 → load that row. Deleted account → 401.

  5. routers/auth.py

    Route body is one line: return user → 200 {"id": 1, "email": "…"}.

  1. multipart

    Client sends file=@bill.jpg plus Authorization: Bearer eyJ….

  2. deps.py

    No token → 401 before the photo is even read. Bills are per-user from the first byte.

  3. routers/bills.py

    Only image/jpeg and image/png (else 415); reads at most 5 MB + 1 byte (else 413).

  4. services/extraction.py

    One Gemini call: the photo goes in as types.Part.from_bytes(...), the shape in as response_schema=BillDraft. The blocking SDK call runs in a thread so the event loop stays free.

  5. Gemini

    Constrained JSON comes back; response.parsed is already a BillDraft. Pydantic rejected anything that doesn't fit — no prose to parse.

  6. services/checks.py

    check_bill(draft) treats that reply as untrusted: maths, ISO date, currency, sane bounds.

  7. branch

    Gemini down, key wrong, model missing → 502, nothing saved. The photo bytes are dropped here; nothing was written to disk.

  8. response

    200 {"draft": {…}, "problems": []} — a draft that exists only in this response. POST /bills/confirm re-checks the edited draft and only then inserts the row (201, or 422 with the fields to fix).

Reuse this pattern Depends(get_current_user) is the only line you add to protect a route — POST /bills/extract and POST /bills/confirm both do exactly that, and GET /expenses will in Phase 6.

5. Hashing & JWT — the two security ideas

Everything else in auth is plumbing built around these two mechanisms.

🔒 bcrypt: passwords are never stored

in:   secret123
      ↓  bcrypt.hashpw(salt, rounds=12)
out:  $2b$12$Kix6hbh1N9Yc3f0u2Vq0Xe…
  • Salt — same password → different hash each time.
  • Slow on purpose — ~200 ms per check; brute force becomes expensive.
  • 72-byte cap — why the schema says max_length=72.
  • Login compares with checkpw() — never “hash the input, string-equal”.

🪪 JWT: the token carries identity

header
alg + type
payload — {"sub": "1", "exp": 1770…}
user id + expiry
signature
HMAC-SHA256
✍️ signed with SECRET_KEY (in .env) 🕵️ tamper with any byte → signature fails → 401 ⏱️ past exp → 401
  • Stateless: restart the server, nobody is logged out.
  • Anyone holding SECRET_KEY can mint tokens — guard it like a password.
The three checks you must be able to explain out loud 1) wrong password at login → 401 with a generic message · 2) forged/expired token → decode fails → 401, route body never runs · 3) password never round-trips — hashed on write, and response_model=UserOut blocks the hash from ever leaving.
The same instinct, now in the bill route “Reply in JSON” in a prompt is the text version of storing a password in plain text — works until it doesn't. So the Gemini call constrains the reply with response_schema, check_bill() re-validates it (money in rupees as exact decimals, ISO dates, maths), and nothing reaches the table without a human confirming.

8. What's next (and where it goes)

  • Phase 1 · Authentication — DONE register / login / me, bcrypt, JWT, get_current_user. Verified end-to-end.
  • Phase 2 · The bill shape — DONE schemas/bill.py (BillDraft, BillItem, Problem) and models/expense.py. Money as rupees in Decimal (total, round_off, items[].amount), dates ISO, items as JSON.
  • Phase 3–4 · Photo → structured draft — DONE POST /bills/extract → services/extraction.py → one Gemini call with response_schema=BillDraft. No plain-text describe step; we went straight to the constrained shape.
  • Phase 5 · Check before you save — DONE check_bill() reruns on the edited draft in POST /bills/confirm: maths (line amounts + printed round-off, ±0.02 with a round-off / ₹1.00 cashier rounding without one), ISO date, currency, bounds. Wrong total → 422, never a silent save.
  • Phase 6 · List, demo, ship — NEXT GET /expenses + monthly total, app/static/index.html (upload, fix form, list, Demo button), then 10 real bills through the live link → the N/10 score.

The honest-miss principle

9/10 with a photo of the miss beats 10/10 claimed. The plan's “DONE” means a number you measured and a photo of the bill it got wrong, with a note on why. Build validation so a bad extraction is flagged, never silently saved — that's how you keep the number honest.

9. Word list (the plan's vocabulary → this codebase)

Structured output

An AI reply in exact fields, not a paragraph. Here: response_schema=BillDraft + response_mime_type="application/json", and response.parsed is already a BillDraft.

JSON schema

The rules for that shape: fields, types, required-ness. Here: every file in schemas/; BillDraft.model_json_schema() is what Gemini is constrained to.

response_schema

Gemini's equivalent of a forced tool call: the API is told the reply must match this schema. Here: services/extraction.py.

Vision

The model reads images you send, including paper photos. Here: routers/bills.py sends one inline part, types.Part.from_bytes(...).

Validation

Your own code re-checking before trusting. Here: Pydantic at the edge + check_bill() maths/date/currency in Phase 5.

ISO date

2026-03-12 so 12/03 can't be March or December. Here: the date column + date.fromisoformat() gate.

Async

Waiting without blocking the thread. Here: every route; the blocking Gemini SDK call runs in a worker thread via run_in_threadpool.

Dependency

FastAPI runs it before a route (e.g. get_current_user). Here: deps.py.

Lifespan

Code that runs at server start/stop. Here: creates tables in app/app.py.
