2. Folder structure

Each folder answers one question. When you add a feature, you add one file to each folder — you rarely touch files from other features.

fastapi2/
├── main.py               # entry point: how do I start the server?
├── .env                  # secrets (git-ignored). Copy from .env.example
├── docs/                 # beginner docs: ARCHITECTURE.md, AUTH.md
└── app/
    ├── app.py             # the app: startup hook + list of routers
    ├── config.py          # settings from .env (SECRET_KEY, token life)
    ├── deps.py            # shared protection: token → user
    ├── routers/            # "the web desk"  — which URL, which status
    │   └── auth.py         # POST /auth/register, /auth/login, GET /auth/me
    ├── schemas/            # "the form"       — exact fields and types
    │   └── auth.py         # UserCreate, UserLogin, TokenResponse, UserOut
    ├── services/           # "the workshop"   — HOW things are done
    │   ├── db.py            # async database engine + session per request
    │   └── auth.py         # bcrypt hash/verify, JWT create/decode
    └── models/             # "the warehouse"  — tables and columns
        └── user.py          # users: id, email, hashed_password, created_at
routers/ = URL & HTTP schemas/ = data shape services/ = logic models/ = storage deps.py = who is calling
Naming pattern for the future Feature expenses will add models/expense.py, schemas/bill.py, routers/expenses.py — auth files stay untouched.

3. The four layers (and the one rule)

Arrows point down only. A model never imports a router; a service never knows HTTP exists. That rule is what keeps code testable and swappable.

Notice

Schemas run first. Garbage JSON never reaches your logic — Pydantic rejects it with 422.

Notice

Deps run before route bodies. No token? Your endpoint code never even executes.

Notice

Services are plain functions. You can test verify_password() without a server or a browser.

4. A request's life, step by step

Pick an endpoint and follow one request from the wire to the database and back. These are the exact three routes that exist today.

  1. routers/auth.py

    FastAPI matches POST /auth/register and hands the JSON body over.

  2. schemas/auth.py

    Pydantic checks UserCreate: email present, password 6–72 chars. Wrong? → 422, stop here.

  3. services/db.py

    A fresh database session opens; query: SELECT * FROM users WHERE email = ?.

  4. branch

    Email already exists → 409 Conflict. (Never reveal whether a password was right — same idea later on login.)

  5. services/auth.py

    hash_password() runs bcrypt with a random salt → a hash string. The plain password is discarded.

  6. models/user.py

    New users row is inserted and committed.

  7. response

    201 {"id": 1, "email": "ana@example.com"} — shaped by UserOut, so the hash can't leak.

  1. routers/auth.py

    FastAPI matches POST /auth/login.

  2. schemas/auth.py

    Pydantic validates UserLogin → bad shape is 422.

  3. services/db.py

    Look up the user by email (lower-cased, so Ana@ = ana@).

  4. services/auth.py

    verify_password() → wrong password or unknown email → same 401 message. Attackers can't probe which emails exist.

  5. services/auth.py

    create_access_token(user_id) signs a JWT: {"sub": "1", "exp": …} + SECRET_KEY.

  6. response

    200 {"access_token": "eyJ…", "token_type": "bearer"}. The server stores nothing — the token is the session.

  1. header

    Client sends Authorization: Bearer eyJ….

  2. deps.py

    get_current_user runs before the route body. No header → 401, full stop.

  3. services/auth.py

    decode_access_token() verifies the signature and expiry. Forged or expired → 401.

  4. models/user.py

    Token says sub=1 → load that row. Deleted account → 401.

  5. routers/auth.py

    Route body is one line: return user → 200 {"id": 1, "email": "…"}.

Reuse this pattern Depends(get_current_user) is the only line you add to protect a future route — e.g. POST /bills (photo upload) and GET /expenses.

5. Hashing & JWT — the two security ideas

Everything else in auth is plumbing built around these two mechanisms.

🔒 bcrypt: passwords are never stored

in:   secret123
      ↓  bcrypt.hashpw(salt, rounds=12)
out:  $2b$12$Kix6hbh1N9Yc3f0u2Vq0Xe…
  • Salt — same password → different hash each time.
  • Slow on purpose — ~200 ms per check; brute force becomes expensive.
  • 72-byte cap — why the schema says max_length=72.
  • Login compares with checkpw() — never “hash the input, string-equal”.

🪪 JWT: the token carries identity

header
alg + type
payload — {"sub": "1", "exp": 1770…}
user id + expiry
signature
HMAC-SHA256
✍️ signed with SECRET_KEY (in .env) 🕵️ tamper with any byte → signature fails → 401 ⏱️ past exp → 401
  • Stateless: restart the server, nobody is logged out.
  • Anyone holding SECRET_KEY can mint tokens — guard it like a password.
The three checks you must be able to explain out loud 1) wrong password at login → 401 with a generic message · 2) forged/expired token → decode fails → 401, route body never runs · 3) password never round-trips — hashed on write, and response_model=UserOut blocks the hash from ever leaving.
Plan-level traps that apply later (same spirit) “Reply in JSON” in a prompt is the text version of storing a password in plain text — works until it doesn't. Use tool use / structured outputs; validate with Pydantic before saving; store money as integers in paise; ask Claude for ISO dates.

8. What's next (and where it goes)

  • Phase 1 · Authentication — DONE register / login / me, bcrypt, JWT, get_current_user. Verified end-to-end.
  • Phase 2 · Design the shape on paper — NEXT Write down every field: shop, date, total, currency, items(name, qty, price). Required or not? → then models/expense.py + a matching table.
  • Phase 3 · Get the photo to Claude Upload route (JPG/PNG, shrink first) → plain-text description of bill #1. Checkpoint: it describes your real bill correctly.
  • Phase 4 · Force the shape One tool (save_bill) whose input schema is your form; require Claude to use it. Read the tool input as your data.
  • Phase 5 · Check before you save Pydantic validation + items-sum-to-total maths check. Fail → 422 with highlighted fields; save only on user confirm.
  • Phase 6 · List, demo, ship “My Expenses” + monthly total, 5 sample bills, push, then run 10 real bills (printed / handwritten / crumpled / Malayalam) and write down the score.

The honest-miss principle

9/10 with a photo of the miss beats 10/10 claimed. The plan's “DONE” means a number you measured and a photo of the bill it got wrong, with a note on why. Build validation so a bad extraction is flagged, never silently saved — that's how you keep the number honest.
