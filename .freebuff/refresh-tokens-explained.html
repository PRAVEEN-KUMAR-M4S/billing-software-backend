1 · The problem with one token

A JWT is stateless: the server doesn't store it, it just checks the signature. Great for speed — terrible for control. You can't un-issue one, so you must pick its lifetime before you know if it will be stolen. That forces an impossible trade-off:

One long-lived token old setup · 24 h

Stay logged in for a day, zero friction. But the token is a key that works until it expires. Steal it once and you're the user until midnight — and "logout" does nothing, because there's nothing stored to delete.

✗ Convenient but uncontrollable

One short-lived token e.g. 15 min

A thief gets at most 15 minutes. But so does the legitimate user — every quarter-hour they get 401 and must type their password again. Nobody ships that.

✗ Safe but unusable

The escape hatch: use both. A short-lived token for everyday requests, plus a long-lived token whose only job is to mint new short-lived ones. Make the long one stateful (a database row) and it becomes controllable: revocable, single-use, replaceable.

Why the refresh token can be revoked: because the server has state for it — a row. A row can be deleted. That's the whole trick: short + stateless for speed, long + stateful for control.

3 · One month of login, zoomed twice

The month view: access tokens burn down every 30 minutes and are replaced silently. The refresh token itself changes too — each refresh rotates it. In 30 days one login causes ~1,440 refreshes; the user types their password once.

Day 0 — login
password checked once → pair #1 issued
≈1,440 refreshes
each one: old refresh deleted, new pair issued
Logout
refresh row deleted → no new pairs, ever

One horizontal rail = one 30-day refresh token's life. Ticks = 5-day marks.

Zoom in on a single refresh — the moment of rotation

This is the security core. Rotation means the client's refresh token is a one-time pad: after use it no longer exists on the server.

Dies at the server

Row token_hash = h(A) is deleted in the same commit that issues the new pair. Replaying token A → 401

⟶
Born at the server

New row h(B) + fresh access token. Client now holds pair B; A is garbage everywhere.

Side effect worth noticing: the access token is not replaced retroactively. Old (not-yet-expired) access tokens keep working until they expire. That's accepted in exchange for statelessness — and it's exactly why the access lifetime was cut from 24 h to 30 min.

4 · The refresh call, step by step

What POST /auth/refresh actually does, mapped to the code in app/routers/auth.py. Every failure exits with the same message — no hints for attackers.

  1. Hash what arrived
    hash_token(data.refresh_token) — sha256. The raw token never matches anything in the DB.
  2. Look up the hash
    select(RefreshToken).where(…) → row missing? 401
  3. Check the clock
    row.expires_at < utcnow() → expired? 401
  4. Load the human
    session.get(User, row.user_id) → account gone? 401
  5. Kill the used token
    await session.delete(row) — rotation happens here, not in a separate "revoke" call.
  6. Issue the new pair — atomically
    _issue_tokens() inserts the new row and commit()s steps 5+6 together. Half-done rotation is impossible.
@router.post("/refresh", response_model=TokenResponse)
async def refresh(data: RefreshRequest, session=…):
    row = await session.scalar(
        select(RefreshToken).where(
            RefreshToken.token_hash == hash_token(data.refresh_token)))
    if row is None or row.expires_at < utcnow():
        raise HTTPException(401, "Invalid or expired refresh token")

    user = await session.get(User, row.user_id)
    if user is None:
        raise HTTPException(401, "Invalid or expired refresh token")

    # Rotate: delete the used token, then issue the
    # new pair (one atomic commit).
    await session.delete(row)
    return await _issue_tokens(user, session)
POST /auth/logout is steps 1–2 + delete, returning 204 even when the token is unknown — logout must never leak what exists.

5 · What the database actually stores

One new table, four columns. The row below is the real one created during today's live test (the hash column is what's actually on disk — the raw token exists only in the client).

ColumnTypeWhy
idINTEGER PKrow identity
token_hashString(128), uniquesha256 of the token — the raw token is never stored
user_idFK → users.idwhose session this is; indexed for lookups
expires_atDateTimelogin + 30 days, stored as naive UTC (SQLite drops timezones)

models/refresh_token.py → real row from test.db:

(2, 2, '56fa7ff5550403696f1b875f7617012fa5033fbd58cbd761af6d1729b52814cc', '2026-11-02 16:02:19.639277')
Why hash it? If the DB leaks, the attacker gets hashes. A sha256 preimage of a 256-bit random string is not computable — the leak is useless for logging anyone in.
Why sha256 and not bcrypt? bcrypt is slow on purpose — for human-chosen passwords. The refresh token has 256 random bits; there's nothing to brute-force, so fast hashing costs nothing.

7 · What each attack gets (and doesn't get)

  
The design's worth shows up when things go wrong. Four scenarios, no optimism.


  

    

      
ScenarioWhat the attacker achievesWhat stops them

      
        
Access token stolen
            Acts as the user… for ≤ 30 minutes
            Statelessness cuts the blast radius to the expiry — this is why it's short now

        
Refresh token stolen
            One refresh… once. The legit client's next refresh 401s (its token was already consumed)
            Single-use rotation. A failed legit refresh is the theft alarm

        
Database leak
            Gets 64-char hashes, no tokens, no passwords (bcrypt for those)
            sha256 of 256 random bits has no shortcut

        
Token guessing
            Nothing — probability ~2−256
            secrets.token_urlsafe(32)

9 · The live test that proved it (all real output)

  
Run against the actual server, October 3. Paste-safe.

  


BASE=http://127.0.0.1:8000

# login → get the pair
curl -s -X POST $BASE/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"refresher@example.com","password":"secret123"}'
# → {"access_token":"…","refresh_token":"…43 chars…","token_type":"bearer"}   200

# rotate: trade RT-1 for pair 2
curl -s -X POST $BASE/auth/refresh -H 'Content-Type: application/json' \
  -d '{"refresh_token":"<paste RT-1>"}'                                       # 200 new pair

# replay RT-1 — it was consumed
curl -s -X POST $BASE/auth/refresh -H 'Content-Type: application/json' \
  -d '{"refresh_token":"<paste RT-1>"}'
# → {"detail":"Invalid or expired refresh token"}                              401

# logout kills RT-2, then RT-2 is dead too
curl -i -X POST $BASE/auth/logout -H 'Content-Type: application/json' \
  -d '{"refresh_token":"<paste RT-2>"}'                                       # 204
curl -s -X POST $BASE/auth/refresh -H 'Content-Type: application/json' \
  -d '{"refresh_token":"<paste RT-2>"}'                                       # 401
