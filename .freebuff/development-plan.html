4. AI integration — the core, kept small

This is the part that feels scary and isn't. The entire AI feature is one module with one public function. Everything else is ordinary backend work you already know.

Fact 1

One call per bill

No agents, no chains, no loops. One HTTP request to Gemini's API, one response, done.

Fact 2

You define the shape

Your Pydantic schema becomes response_schema. One definition, three users (the model, the checks, confirm).

Fact 3

You read the parsed reply

response.parsed is already a BillDraft. Not text to parse — an object Pydantic validated.

Step A — Vision: how the photo actually reaches Gemini

# One call: prompt text + one inline image part
from google.genai import types

contents = [
  "Extract this bill.",
  types.Part.from_bytes(data=photo_bytes, mime_type="image/jpeg"),  # or image/png
]
# The SDK base64-encodes the bytes for you — no manual base64 step.
  • Inline data rides inside the request (total request limit: 20 MB). Larger files would need the Files API; a bill photo never does.
  • Phone photos are big and images are tokenised by pixels, so shrink before sending (max edge ~1500 px) — faster and cheaper. Not done yet: the 5 MB cap is the only limit today, so resizing is the next optimisation.
  • Paper photos, handwriting, crumpled folds, Malayalam text — vision reads what it can and must mark the rest null + a note. The prompt says that; the checks enforce it.
  • The bytes are never stored — no uploads/ folder, no path column.

Step B — Structured output: why “reply in JSON” is banned

Fragile

“Please reply in JSON”

→ Here's the JSON you asked for:
  ```json
  { "shop": "Lulu", ... }   # sometimes
  # sometimes wrapped in prose, sometimes
  # truncated, sometimes wrong key names

Works most of the time; breaks at the worst time. Parsing, trimming, retrying — all yours.

Reliable

One constrained response: response_schema

config=types.GenerateContentConfig(
  response_mime_type="application/json",
  response_schema=BillDraft,      # ← your Pydantic shape
)
# → response.parsed is a BillDraft.
#   The API refuses JSON that doesn't fit.

The API refuses any reply that doesn't fit the schema. No prose, no parsing, no “most of the time”. Gemini has no Claude-style forced tool call — response_schema is the equivalent guarantee.

The whole AI module, honestly app/services/extraction.py is one public function: it sends one image part, passes response_schema=BillDraft, and returns response.parsed. Phases 3 and 4 collapsed into one step — the plain-text describe route was skipped because the constrained call is the same pipe. The router only knows extract_bill, never Gemini.

Step C — The module as it shipped

# app/services/extraction.py — the ONLY file that talks to Gemini
from google import genai
from google.genai import types
from app.schemas.bill import BillDraft

client = genai.Client(api_key=GEMINI_API_KEY)   # built lazily, so the app boots without a key

def extract_bill(photo_bytes: bytes, mime_type: str) -> BillDraft:
    response = client.models.generate_content(
        model=GEMINI_MODEL,                     # from .env, never hardcoded
        contents=[
            "Extract this bill.",
            types.Part.from_bytes(data=photo_bytes, mime_type=mime_type),
        ],
        config=types.GenerateContentConfig(
            system_instruction=EXTRACTION_PROMPT,   # versioned in config.py
            response_mime_type="application/json",
            response_schema=BillDraft,              # ← THE SHAPE, reused not copied
            temperature=0,
        ),
    )
    return response.parsed   # untrusted → validated → usable

Parameter names drift between SDK versions — this is google-genai 2.32. A JSON fallback (BillDraft.model_validate_json(response.text)) covers a reply that arrived as text, and every failure becomes a 502 instead of a half-parsed bill.

Step D — The prompt: short, fixed, versioned

# config.py — one system instruction, written once, versioned
PROMPT_VERSION = "v1"
EXTRACTION_PROMPT = """
Extract this receipt or bill into the provided schema.
- date: ISO YYYY-MM-DD; never guess DD/MM vs MM/DD, null if ambiguous
- currency: ISO 4217 code (INR unless the bill says otherwise)
- money: whole minor units (paise); no floats, no currency symbols
- if a value is unreadable, set it to null and explain why in notes
- never guess: an honest null beats a wrong number
"""
  • It lives in config.py — one owner, sent as system_instruction on every call.
  • PROMPT_VERSION = "v1" is stored in an expenses.prompt_version column, so when the score changes you know which prompt produced which row.
  • No “reply in JSON” in the prompt — the schema does that job. Asking in prose is the fragile version of a guarantee the API already gives you.

What one call costs you

DimensionRealityWhat to do
LatencyA few seconds per bill — vision + constrained JSON isn't instant. Ship a simple “Extracting…” spinner; no background jobs needed at this scale.
CostRoughly pennies per bill on a mid-tier model; images are tokenized by pixels, so smaller = cheaper. (Check the pricing page — it changes.) Resize photos; one call per upload; no retry loops.

5. The cashier check (validation design)

Your code re-checks the reply before trusting it — like a cashier double-checking a bill. Each check is a tiny pure function in services/checks.py, so you can test them without a server, a photo, or Gemini.

#CheckCatchesOn failure
1Pydantic schema — required fields, types, lengths Missing/incorrect structure from the tool“Couldn't read this bill” → fix form
2Maths — Σ(qty × price) ≈ total, tolerance ±2 paise (rounding) Hallucinated or mis-added items — the #1 AI failureFlag total + items, show both numbers
3ISO date — date.fromisoformat() succeeds 12/03 ambiguity, impossible datesFlag the date field
4Currency — in your allowed set (e.g. INR) Model assuming $ on an Indian billFlag currency, default prefilled
5Unreadable — nulls allowed where the prompt promised them Blurry photos, folded cornersNot an error → straight to fix form
6Sane bounds — total > 0, qty ≥ 1, shop non-empty Garbage numbersFlag the field

The state machine (this is the whole UX)

Uploading → Extracting (Gemini) → Ready (all checks pass) → 💾 Saved (user confirmed)
Uploading → Extracting ↙ Needs fix (fields highlighted) → edit → Re-check

Hard rule: there is no arrow from “Extracting” to “Saved”. The only path into the database runs through a human confirming a check-passing draft. That's how the honest 9/10 number stays honest.

6. Phase-by-phase: files, work, checkpoint

Each phase = one new idea + a handful of files. Do them in order; the checkpoint is a real test, not a feeling.

Phase 2 — The shape DONE

Built exactly as planned, one name everywhere:

  • schemas/bill.py — BillDraft(shop, date, currency, total_minor, items, notes), BillItem(name, qty, price_minor), Problem(field, message)
  • models/expense.py — same fields + user_id, prompt_version, created_at; items as a JSON column, date as a SQL date
  • No image_path column — the photo is never stored, so there is no path to keep
Checkpoint passed: one Pydantic model, three users — Gemini, the checks, confirm.

Phase 3 — Photo → structure DONE

Shipped as one route, with no plain-text describe step — the constrained call is the same pipe:

  • routers/bills.py — POST /bills/extract: auth first, JPG/PNG only (415), 5 MB cap (413), then the same bytes go to Gemini — no disk write
  • services/extraction.py — extract_bill(bytes, mime) → BillDraft
  • .env — GEMINI_API_KEY, GEMINI_MODEL; dep: uv add google-genai
  • Resizing with Pillow is still the obvious next optimisation
Checkpoint: request construction verified against the live API; real photos await a key (Phase 6 eval).

Phase 4 — Constrain the shape DONE

Gemini's equivalent of a forced tool, one definition reused:

  • response_mime_type="application/json" + response_schema=BillDraft; response.parsed is the draft
  • Route returns the draft and still writes nothing to the database
  • A schema/JSON failure becomes a 502 — never a half-parsed bill
  • Prompt lives in config.py with PROMPT_VERSION = "v1"
Checkpoint passed: nested items and nullable fields convert cleanly to Gemini's schema.

Phase 5 — Check before save DONE

The cashier (§5) plus the human step:

  • services/checks.py — check_bill(draft) → list[Problem], pure, no I/O
  • Response: {draft, problems[]}; each problem carries field + message
  • POST /bills/confirm — accepts the edited draft, re-runs every check, then writes the row with user_id from the token
  • Adversarial case tested: hand-edit the total → 422, and the table stays empty
Checkpoint passed: wrong total flagged, never saved silently.

Phase 6 — List, demo, ship NEXT

Finish the loop a user can see. Right now a saved bill exists but no route can read it back:

  • routers/expenses.py — GET /expenses (your rows, newest first) + monthly total (sum in SQL, paise → display)
  • app/static/index.html — tiny page served by FastAPI: upload form, fix form, list with monthly total, Demo button
  • Demo = 5 photos in samples/ run through the real pipeline
  • Deploy (see §7), then 10 real bills through the live link → write down the score
Done means: “N/10 extracted correctly” + the miss photo with a note.

Optional — Eval script · 1 hour, high value

Turns your score from a claim into a command you can rerun after any change:

  • evals/bills/ — the 10 photos + expected.json (right answers)
  • uv run python -m evals.run — runs each photo through extract_bill + checks, prints score: 9/10 and what failed
  • Costs ~10 calls per run (pennies) — run it before you change the prompt
Why: “9/10” on your card, reproducible in front of anyone.

7. Decisions to make (recommended defaults)

Four calls that shape everything after them. Recommended answers first — accept them or overrule them consciously, but decide in Phase 2, not Phase 5.

1 · How do we store money?
Recommended: whole minor units — total_minor INTEGER (paise). Display ÷100.

✓ Exact arithmetic, no float drift, matches the plan's warning. ✗ You must remember “this number is paise” — name columns *_minor so future-you knows.

2 · Items: second table or JSON column?
Recommended: JSON column to start (SQLite + SQLAlchemy JSON type).

✓ One table, trivial reads, no joins — the plan explicitly allows it. ✗ “find all bills containing coffee” needs a real table later — a deliberate, cheap upgrade.

3 · Which currency, and which Gemini model?
Chosen: INR (bills include Malayalam) in config.py; gemini-3.6-flash as the default in .env.

Model ids change fast, so the name lives in GEMINI_MODEL, never in code. gemini-3.5-flash is deprecated and now routes to 3.6 anyway; Gemini 2.5 models are restricted to prior users, so a new project should not start there. Confirm your key can see the model in AI Studio before the eval run. ISO dates + explicit currency in the prompt either way.

4 · Where does it go live?
Recommended: one simple PaaS (Render / Railway / Fly) with SQLite only if it has a persistent disk; otherwise add a small Postgres.

Gotcha: on ephemeral hosts, SQLite wipes on every redeploy — fine for a demo day, brutal mid-eval. Decide before Phase 6, not during it. The DATABASE_URL switch is the only code change.

8. What we will NOT build (on purpose)

Every item below is real engineering someone eventually needs — and all of it is a distraction from “10 real bills, measured”. Cut list is part of the plan.

No AI complexity

  • No agent loops / multi-step chains
  • No LangChain or framework — the SDK is 3 calls
  • No retries-with-backoff beyond “user clicks again”
  • No fine-tuning, no embeddings, no vector DB
  • No OCR fallback if Gemini fails — report and move on

No backend ceremony

  • No message queues / background workers (a few seconds is fine)
  • No Redis, no cache layer
  • No refresh tokens / email verification (still!)
  • No Alembic migrations — create_all while schema is young
  • No rate limiting until public

No product scope

  • No categories, budgets, charts, CSV export
  • No sharing / teams / roles
  • No photo storage at all — bytes are read, sent once, dropped
  • No edit-history / audit trail
  • No mobile app — one static HTML page
Rule of thumb If it doesn't move the N/10 number or the demo forward this fortnight, it's Phase 7+. Write it on a “later” list instead of building it “while we're here”.

10. The score card (definition of done)

The measurement

SET: 10 real bills — printed, handwritten,
     crumpled, one in Malayalam
RUN: each through the LIVE deployed link
SCORE: fully-correct extractions / 10
       (shop, date, total, currency, items all right)

CARD: "9 / 10 bills extracted correctly"
      + photo of the miss + a note on why

The honest miss is worth more than the nine hits — it proves you measured instead of cherry-picked.

What you'll be able to say afterwards

  • “I built structured extraction with a constrained schema — the AI fills my form, my code validates it.”
  • “I can show the exact architecture — layers, one owner per state, one AI module.”
  • “I have a live link and a measured number, plus a documented failure mode.”
  • “Validation runs before persistence — bad data can't be saved silently.”
That's the hire-ready story Working system + measured result + honest analysis of the miss > a bigger demo nobody measured.

11. New words for this phase

response_schema

Gemini's equivalent of a forced tool call: the reply must fit this Pydantic shape. response.parsed hands back the object — the guarantee behind reliable structured output.

inline part

types.Part.from_bytes(...) — image bytes inside the request itself (the SDK base64-encodes them for you). One bill photo easily fits the 20 MB cap.

Minor units

Money as integers in the smallest unit (paise). ₹12.50 → 1250. Floats are banned from money.

Tolerance

Allow a tiny gap (±2 paise) before calling the maths wrong — rounding isn't an error. Misses beyond tolerance become a flagged field.

Untrusted input

Data you treat as user-supplied until validated — Gemini's reply joins this category permanently — check_bill() is what makes that real.

Eval harness

A fixed set of inputs + expected outputs you rerun to get a score. Turns “I think it works” into a number.

Draft vs persisted

A draft exists only in a response; persisted means a database row. Only confirm crosses that line.

Prompt version

The exact instruction text used for an extraction — log it so score changes are explainable.

content part

One piece of a Gemini request: a text Part, or inline image bytes. contents is a list of these.
