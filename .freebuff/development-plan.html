2. The plan at a glance

Same checkpoints as the project brief, ordered so each phase has exactly one new idea. Total: 1–2 weekends. Nothing starts before the checkpoint above it passes.

1

Authentication DONE

register / login / me, bcrypt + JWT, the layer structure every later phase uses.

Checkpoint passed: all six behaviours verified live (201 / 409 / 401 / 200).
2

Design the shape · half day

Write every field on paper first — shop, date, total, currency, items[] (name, qty, price) — then mirror it exactly in one Pydantic schema and one database table. Money as whole paise, dates as ISO.

Checkpoint: you can explain every field and its type without looking.
3

Photo → words · half day

Upload endpoint (JPG/PNG, size cap, shrunk before sending) that sends the image to Claude and returns a plain-text description. No structure yet — just prove the pipe works.

4

Define one tool, save_bill, whose input schema is your shape, and force Claude to use it. The tool's input is your structured output. Validate with Pydantic.

5

Check before you save · 1 day

The cashier double-check: maths (items sum to total, small rounding tolerance), ISO date parse, currency sanity, “unreadable” handling. Problems → editable fix form with fields highlighted → save only after the user confirms.

Checkpoint: a bill with a wrong total gets flagged and is never saved silently.
6

List, demo, ship · 1 day + eval

“My Expenses” list with a monthly total, a demo button that runs 5 sample bills, deploy, then run your 10 real bills (printed, handwritten, crumpled, one in Malayalam) through the live link and write down the number.

Checkpoint / done means: a measured score like “9/10”, plus a photo of the one it got wrong with a note on why. The honest miss is worth more than the nine hits.

4. AI integration — the core, kept small

This is the part that feels scary and isn't. The entire AI feature is one module with one public function. Everything else is ordinary backend work you already know.

Fact 1

One call per bill

No agents, no chains, no loops. One HTTP request to Claude's API, one response, done.

Fact 2

You define the shape

Your Pydantic schema becomes the tool's input schema. One definition, three users (tool, validator, docs).

Fact 3

You read the input

The tool's filled-in input is the structured output. Not text to parse — a dict Pydantic validates.

Step A — Vision: how the photo actually reaches Claude

# You send a content list: one image block + one text block
content = [
  {"type": "image",  "source": {"type": "base64",
                                "media_type": "image/jpeg",   # or image/png
                                "data": base64.b64encode(photo_bytes).decode()}},
  {"type": "text",   "text": "Extract this bill."}
]
  • base64 = turning bytes into text so they can ride inside JSON. That's the whole trick.
  • Phone photos are big; shrink before sending (max edge ~1500 px) — faster, cheaper, still readable. Optional at first; add when you start sending 4 MB photos.
  • Paper photos, handwriting, crumpled folds, Malayalam text — all fine; vision reads what it can and should mark the rest unreadable (you'll say that in the prompt).

Step B — Forced tool use: why “reply in JSON” is banned

Fragile

“Please reply in JSON”

→ Here's the JSON you asked for:
  ```json
  { "shop": "Lulu", ... }   # sometimes
  # sometimes wrapped in prose, sometimes
  # truncated, sometimes wrong key names

Works most of the time; breaks at the worst time. Parsing, trimming, retrying — all yours.

Reliable

One forced tool: save_bill

tools=[SAVE_BILL_TOOL],
tool_choice={"type": "tool", "name": "save_bill"}
# → response contains a tool_use block whose
#   .input is a dict shaped EXACTLY like your
#   schema. Guaranteed by the API, not by luck.

The API refuses any reply that doesn't fill the tool. No prose, no parsing, no “most of the time”.

The whole AI module, honestly app/services/extraction.py will be ~40 lines: a tool definition built from your Pydantic schema, one function that base64-encodes the photo and calls client.messages.create(...) with the forced tool, and returns BillData.model_validate(tool_use.input). Phase 3 puts a plain-text version of the same function in place; Phase 4 swaps the body — the router never changes.

Step C — The skeleton you'll write in Phase 4

# app/services/extraction.py  — the ONLY file that talks to Claude
import base64, os
import anthropic
from app.schemas.bill import BillData          # ← THE SHAPE (Phase 2)

client = anthropic.Anthropic()                 # reads ANTHROPIC_API_KEY from .env

SAVE_BILL_TOOL = {
    "name": "save_bill",
    "description": "Save the bill the user photographed.",
    "input_schema": BillData.model_json_schema(),   # ← schema reused, not copied
}

def extract_bill(photo_bytes: bytes, media_type: str) -> BillData:
    response = client.messages.create(
        model=os.getenv("ANTHROPIC_MODEL"),     # set in .env — check docs for current ids
        max_tokens=1024,
        tools=[SAVE_BILL_TOOL],
        tool_choice={"type": "tool", "name": "save_bill"},   # force it
        messages=[{
            "role": "user",
            "content": [
                {"type": "image", "source": {"type": "base64",
                     "media_type": media_type,
                     "data": base64.b64encode(photo_bytes).decode()}},
                {"type": "text", "text": PROMPT},            # short, fixed prompt
            ],
        }],
    )
    tool_use = next(b for b in response.content if b.type == "tool_use")
    return BillData.model_validate(tool_use.input)   # untrusted → validated → usable

Exact parameter names can drift between SDK versions — keep the Anthropic docs page on tool use open next to you. The shape of the code above won't change.

Step D — The prompt: short, fixed, versioned

# One system instruction, written once:
PROMPT = """
Extract this receipt/bill into the save_bill tool.
- dates: ISO format YYYY-MM-DD (never DD/MM vs MM/DD)
- money: whole minor units (paise); no floats, no currency symbols
- if a field is unreadable or blurry, set it to null and say why in notes
- never guess: an honest null beats a wrong number
"""
  • Put it in config.py (or a prompts.py) — one owner, not scattered inside functions.
  • Log which prompt you used with each extraction (a column or a log line) so when the score changes you know why.
  • If the model you pick supports structured outputs natively, that's an equivalent alternative to forced tools — check current docs; either way, never plain-text JSON.

5. The cashier check (validation design)

Your code re-checks the reply before trusting it — like a cashier double-checking a bill. Each check is a tiny pure function in services/checks.py, so you can test them without a server, a photo, or Claude.

#CheckCatchesOn failure
1Pydantic schema — required fields, types, lengths Missing/incorrect structure from the tool“Couldn't read this bill” → fix form
2Maths — Σ(qty × price) ≈ total, tolerance ±2 paise (rounding) Hallucinated or mis-added items — the #1 AI failureFlag total + items, show both numbers
3ISO date — date.fromisoformat() succeeds 12/03 ambiguity, impossible datesFlag the date field
4Currency — in your allowed set (e.g. INR) Model assuming $ on an Indian billFlag currency, default prefilled
5Unreadable — nulls allowed where the prompt promised them Blurry photos, folded cornersNot an error → straight to fix form
6Sane bounds — total > 0, qty ≥ 1, shop non-empty Garbage numbersFlag the field

The state machine (this is the whole UX)

Uploading → Extracting (Claude) → Ready (all checks pass) → 💾 Saved (user confirmed)
Uploading → Extracting ↙ Needs fix (fields highlighted) → edit → Re-check

Hard rule: there is no arrow from “Extracting” to “Saved”. The only path into the database runs through a human confirming a check-passing draft. That's how the honest 9/10 number stays honest.

6. Phase-by-phase: files, work, checkpoint

Each phase = one new idea + a handful of files. Do them in order; the checkpoint is a real test, not a feeling.

Phase 2 — The shape · half day

Start on paper. Table of fields with types and required/optional marks. Then code it once:

  • schemas/bill.py — BillItem(name, qty, price_minor), BillData(shop, date, currency, total_minor, items, notes)
  • models/expense.py — same fields + user_id, image_path, created_at; items as a JSON column to start
  • Decide money & dates now (see §7) — changing later is painful
Checkpoint: explain every field and its type without looking.

Phase 3 — Photo → words · half day

Prove the pipe before adding structure:

  • routers/bills.py — POST /bills/describe: auth, JPG/PNG check, size cap (e.g. 5 MB), save to uploads/, return text
  • services/extraction.py — describe_bill() → str (no tools yet)
  • .env — ANTHROPIC_API_KEY, ANTHROPIC_MODEL; deps: uv add anthropic
  • Optional: resize with Pillow (worth it before Phase 6)
Checkpoint: plain-text description of your first real bill is correct.

Phase 4 — Force the shape · half day

Swap the body of the service, keep everything else:

  • Add SAVE_BILL_TOOL + forced tool_choice; function now returns BillData
  • Route becomes POST /bills/extract, returns the draft (still no DB write)
  • Delete the “describe” path — one way to do things
  • Try it against: printed, handwritten, crumpled photos
Checkpoint: every reply has exactly your fields, nothing extra.

Phase 5 — Check before save · 1 day

The cashier (§5) plus the human step:

  • services/checks.py — check_bill(bill) → list[Problem], pure
  • Response: {draft, problems[]}; problems carry field + message
  • POST /bills/confirm — accepts edited draft, re-runs checks, then writes the row (auth: only your own bills)
  • Test the adversarial case: hand-edit a total to be wrong → must be flagged, never saved
Checkpoint: wrong total flagged, never saved silently.

Phase 6 — List, demo, ship · 1 day + eval

Finish the loop a user can see:

  • routers/expenses.py — GET /expenses (your rows, newest first) + monthly total (sum in SQL, paise → display)
  • app/static/index.html — tiny page served by FastAPI: upload form, fix form, list with monthly total, Demo button
  • Demo = 5 photos in samples/ run through the real pipeline
  • Deploy (see §7), then 10 real bills through the live link → write down the score
Done means: “N/10 extracted correctly” + the miss photo with a note.

Optional — Eval script · 1 hour, high value

Turns your score from a claim into a command you can rerun after any change:

  • evals/bills/ — the 10 photos + expected.json (right answers)
  • uv run python -m evals.run — runs each photo through extract_bill + checks, prints score: 9/10 and what failed
  • Costs ~10 calls per run (pennies) — run it before you change the prompt
Why: “9/10” on your card, reproducible in front of anyone.

7. Decisions to make (recommended defaults)

Four calls that shape everything after them. Recommended answers first — accept them or overrule them consciously, but decide in Phase 2, not Phase 5.

1 · How do we store money?
Recommended: whole minor units — total_minor INTEGER (paise). Display ÷100.

✓ Exact arithmetic, no float drift, matches the plan's warning. ✗ You must remember “this number is paise” — name columns *_minor so future-you knows.

2 · Items: second table or JSON column?
Recommended: JSON column to start (SQLite + SQLAlchemy JSON type).

✓ One table, trivial reads, no joins — the plan explicitly allows it. ✗ “find all bills containing coffee” needs a real table later — a deliberate, cheap upgrade.

3 · Which currency, and which Claude model?
Recommended: INR (bills include Malayalam) in config.py; a current vision-capable mid-tier model in .env.

Check Anthropic's docs/pricing for the current model id — they change. Put the choice in .env so switching is one line, and note: ISO dates + explicit currency in the prompt either way.

4 · Where does it go live?
Recommended: one simple PaaS (Render / Railway / Fly) with SQLite only if it has a persistent disk; otherwise add a small Postgres.

Gotcha: on ephemeral hosts, SQLite wipes on every redeploy — fine for a demo day, brutal mid-eval. Decide before Phase 6, not during it. The DATABASE_URL switch is the only code change.

8. What we will NOT build (on purpose)

Every item below is real engineering someone eventually needs — and all of it is a distraction from “10 real bills, measured”. Cut list is part of the plan.

No AI complexity

  • No agent loops / multi-step chains
  • No LangChain or framework — the SDK is 3 calls
  • No retries-with-backoff beyond “user clicks again”
  • No fine-tuning, no embeddings, no vector DB
  • No OCR fallback if Claude fails — report and move on

No backend ceremony

  • No message queues / background workers (a few seconds is fine)
  • No Redis, no cache layer
  • No refresh tokens / email verification (still!)
  • No Alembic migrations — create_all while schema is young
  • No rate limiting until public

No product scope

  • No categories, budgets, charts, CSV export
  • No sharing / teams / roles
  • No photo storage in S3 — uploads/ folder
  • No edit-history / audit trail
  • No mobile app — one static HTML page
Rule of thumb If it doesn't move the N/10 number or the demo forward this fortnight, it's Phase 7+. Write it on a “later” list instead of building it “while we're here”.

10. The score card (definition of done)

The measurement

SET: 10 real bills — printed, handwritten,
     crumpled, one in Malayalam
RUN: each through the LIVE deployed link
SCORE: fully-correct extractions / 10
       (shop, date, total, currency, items all right)

CARD: "9 / 10 bills extracted correctly"
      + photo of the miss + a note on why

The honest miss is worth more than the nine hits — it proves you measured instead of cherry-picked.

What you'll be able to say afterwards

  • “I built structured extraction with forced tool use — the AI fills my form, my code validates it.”
  • “I can show the exact architecture — layers, one owner per state, one AI module.”
  • “I have a live link and a measured number, plus a documented failure mode.”
  • “Validation runs before persistence — bad data can't be saved silently.”
That's the hire-ready story Working system + measured result + honest analysis of the miss > a bigger demo nobody measured.

11. New words for this phase

Forced tool choice

Telling the API: “your reply must be a call to this tool.” tool_choice={"type":"tool","name":"save_bill"} — the guarantee behind reliable structured output.

base64

Encoding raw bytes as text so a photo can travel inside JSON. Not compression — it makes files ~33% bigger.

Minor units

Money as integers in the smallest unit (paise). ₹12.50 → 1250. Floats are banned from money.

Tolerance

Allow a tiny gap (±2 paise) before calling the maths wrong — rounding isn't an error. Misses beyond tolerance become a flagged field.

Untrusted input

Data you treat as user-supplied until validated — Claude's reply joins this category permanently.

Eval harness

A fixed set of inputs + expected outputs you rerun to get a score. Turns “I think it works” into a number.

Draft vs persisted

A draft exists only in a response; persisted means a database row. Only confirm crosses that line.

Prompt version

The exact instruction text used for an extraction — log it so score changes are explainable.

content block

One piece of a Claude message: an image block, a text block, a tool_use block. Messages are lists of these.
